# BLASTN-guided candidate-locus discovery and expansion — specification V2

## 1. Status

This is the implementation-ready refinement of
`TASKS/CandidateLoci_blastn/V1.md`. It incorporates every user decision
recorded in V1 and has no open design questions.

This refinement task does not implement the feature. It only:

1. defines the final implementation contract in this V2; and
2. fixes the two pre-implementation regression tests at the end of
   `SCRIPT/CANDIDATE_LOCI/tests/test_candidate_loci.py`.

The implementation task must make those two tests pass without modifying,
skipping, weakening, renaming, or parametrically bypassing them.

## 2. Objective and preserved motivation

Candidate loci are currently inferred only from protein-alignment HSPs. That
can truncate a locus or miss it completely even when a high-similarity
nucleotide alignment identifies the full target interval. A truncated region
prevents the nucleotide locus-alignment transfer strategy from recovering the
complete annotation.

Add an optional BLASTN evidence path that:

1. expands an existing protein-derived candidate when a qualifying BLASTN HSP
   for the same model overlaps and extends it; and
2. discovers a new candidate when a qualifying BLASTN HSP does not overlap an
   already accepted protein-derived or higher-ranked BLASTN-derived candidate.

The BLASTN feature is opt-in. Omitting the BLASTN file must retain the legacy
candidate-locus algorithm and must not perform nucleotide discovery or
boundary adjustment. The implementation should place the main new logic in a
separate focused module and make only small integration changes to the current
candidate-locus code and CLI.

The supplied regression fixture is
`SCRIPT/CANDIDATE_LOCI/tests/data/OsjNip_HIPP_Nip2Nip_Chr04_19814005`:

- `blastp_softmax.tsv` finds all seven expected regions but covers only 918 of
  1,678 bases (54.71%) of `OsjNip_Chr04_19814005`;
- `blastp_default.tsv` completely misses
  `OsjNip_Chr04_19836437` at `Chr4:19835501-19836437`;
- `blastn.tsv` contains qualifying full-length self hits that resolve both
  failures; and
- `ref.gff` defines the seven exact expected gene intervals.

## 3. Final decision record

All significant choices are resolved. The alternatives are retained here to
document why the implementation contract has this shape.

### 3.1 Python API and CLI

Approved: a keyword-only `blastn_file` argument plus a dedicated
`ParametersBlastn` object. The CLI exposes only an optional BLASTN file flag.
Thresholds and format selection are not exposed at CLI level.

Alternatives not selected:

- separate threshold arguments would expand public signatures;
- placing the BLASTN file inside `ParametersCandidateLoci` would mix input
  location with the existing algorithm parameters.

### 3.2 BLASTN input schema

Approved: accept a headerless tab-separated file in which every row has the
same number of fields and that number is at least 12. The first ten fields have
the fixed meanings defined in Section 5. Extra fields are ignored by this
feature. The production command is:

```text
blastn ... -outfmt "6 qseqid sseqid qlen length qstart qend sstart send nident pident gapopen evalue bitscore positive"
```

The final `bitscore` and `positive` fields are not required by candidate-locus
expansion. Exact-14-only and canonical-12-only parsers were rejected because
the user explicitly authorized any consistent schema with at least 12 fields.

### 3.3 Memory strategy

Approved: scan the raw file once and store only minimal records for HSPs that
pass the strict coverage and identity thresholds in a chromosome-keyed
in-memory dictionary. Do not load the complete raw BLASTN table or retain
unused columns.

Chromosome-streaming and external sorting were rejected for the first version
because the qualifying subset is expected to be small and the additional
complexity is not currently justified. The benchmark must still report the
qualifying-hit count and peak memory so this assumption can be revisited with
evidence.

### 3.4 Ranking and conflicts

Approved: use the simple nucleotide quality score
`coverage * identity`. Process higher scores first and genomic starts in
ascending order. Protein-derived candidates always have priority. A BLASTN hit
that overlaps an accepted candidate for a different model is discarded. A new
BLASTN candidate is accepted only when it overlaps neither a protein-derived
candidate nor an earlier, higher-ranked BLASTN candidate.

More elaborate locus clustering, merged-HSP eligibility, and cross-evidence
score competition are deferred under YAGNI.

### 3.5 Nucleotide-only representation

Approved: reuse `CandidateLocus` with explicit source-aware behavior and
BLASTN-derived metrics. Its `prot_len` is the true reference protein length
computed from the model's single-mRNA CDS features, not the nucleotide BLAST
query length. A nucleotide-only candidate serializes only `gene` and `mRNA`
features; it never serializes BLASTN HSPs as CDS features.

Making all protein-only fields optional or introducing a separate final output
type was rejected for this version in favor of a small, source-guarded change.

### 3.6 `expansion=None`

Approved: an explicitly supplied BLASTN file still enables both BLASTN
discovery and BLASTN boundary adjustment when generic expansion is `None`.
`expansion=None` disables arbitrary/default 300/3,000-nt expansion, not
evidence-based BLASTN bounds. Supplying no BLASTN file independently disables
the nucleotide behavior.

## 4. Public API and configuration contract

### 4.1 Configuration type

Add a readable immutable/default-safe configuration type named
`ParametersBlastn` with this public contract:

```python
ParametersBlastn(
    min_coverage: float = 0.85,
    min_identity: float = 0.95,
)
```

Both values are fractions in `[0, 1]` and are inclusive thresholds. Invalid
values must raise an informative `ValueError` before BLASTN rows are used.
The parser format is fixed by Section 5 and is not configurable in V2.

### 4.2 Candidate-locus functions

Extend both entry points without changing any existing positional parameter:

```python
def find_candidate_loci(
    gff_file,
    blast_file,
    params=None,
    chr=None,
    *,
    blastn_file=None,
    blastn_params=None,
) -> dict:
    ...

def find_candidate_loci_from_file(
    gff_file,
    sorted_blast_file,
    params=None,
    chr=None,
    *,
    blastn_file=None,
    blastn_params=None,
) -> dict:
    ...
```

`blastn_file` accepts the same path-like conventions as the existing file
arguments. `blastn_params=None` means use `ParametersBlastn()` when and only
when `blastn_file` is provided. Passing `blastn_params` without
`blastn_file` is a Python API usage error and must raise `ValueError` rather
than silently doing nothing.

The two finalized fixture tests call `find_candidate_loci(...,
blastn_file=blastn_tsv)` and therefore lock this keyword name and position.

### 4.3 CLI

Add one optional argument to `SCRIPT/candidate_loci_VR.py`:

```text
--blastn_table PATH
```

No BLASTN threshold or format flags are added. The CLI uses
`ParametersBlastn()` defaults. It must verify the file exists before creating
or replacing output files. `--chr` applies identically to the protein and
nucleotide tables.

The existing `--min_sim` and `--min_score` flags continue to control final
candidate filtering. There is no new `--min_pc_sym` flag; V1's reference to
that name maps to the existing `--min_sim`/`pc_similarity` behavior.

## 5. BLASTN parsing and eligibility contract

### 5.1 Required columns

The first ten tab-separated fields are fixed:

1. `qseqid`: model/query ID;
2. `sseqid`: target chromosome/contig ID;
3. `qlen`: nucleotide query length;
4. `length`: HSP alignment length;
5. `qstart`;
6. `qend`;
7. `sstart`;
8. `send`;
9. `nident`;
10. `pident`: percentage identity in `[0, 100]`.

Every row must have the same field count and at least 12 fields. Fields 11 and
later are not used. Blank lines may be ignored consistently; nonblank comment
or header lines are not part of the accepted format.

Fail fast with file path and line number when:

- a row has fewer than 12 fields or differs from the first data row's field
  count;
- a required numeric value is malformed, NaN, or infinite;
- `qlen` or `length` is not positive;
- coordinates are not positive 1-based integers;
- normalized query coordinates fall outside `1..qlen`; or
- `pident` is outside `[0, 100]`.

Do not reject an HSP solely because alignment `length` is slightly greater
than `qlen`; a valid gapped alignment can have that shape, and coverage is
still calculated from the reported values.

### 5.2 Eligibility

Assess every HSP independently; never merge HSPs to pass a threshold.

```text
coverage = length / qlen
identity = pident / 100.0
quality = coverage * identity
```

An HSP qualifies when both:

```text
coverage >= min_coverage
identity >= min_identity
```

Compute with unrounded values. Equality at 0.85 coverage or 0.95 identity
passes. Store only qualifying hits and only these values:

- query/model ID;
- chromosome/contig ID;
- nucleotide query length;
- alignment length and identities;
- normalized query bounds;
- normalized subject genomic bounds;
- subject strand;
- coverage, identity, and quality.

Before accepting a qualifying hit, its query/model ID must exist in the model
metadata parsed from the supplied GFF. An unknown ID is an input error with an
informative message naming the ID, BLASTN file, and line. Do not partially
process such a file.

### 5.3 Reference protein-length metadata

Extend the existing GFF-derived model metadata used by candidate scoring and
GFF-based expansion so each model also has its true protein length. Compute it
once while parsing the reference GFF; do not reparse the GFF for each BLASTN
hit or candidate.

For each model/query ID:

1. require exactly one associated `mRNA`;
2. require at least one `CDS` child of that mRNA;
3. calculate each CDS/exon length with inclusive GFF coordinates as
   `end - start + 1`;
4. calculate `coding_length = sum(CDS lengths)`; and
5. calculate `protein_length = coding_length / 3`.

The coding length must be positive and divisible by three so
`protein_length` is a positive integer. Missing mRNA/CDS features, multiple
mRNAs for one model, inconsistent parentage, or a non-divisible coding length
must raise an informative GFF/model validation error naming the model. This
protein length should be added to the current `GeneInfo`-like structure that
already carries coding-region, strand, and intron information.

### 5.4 Coordinates and ordering

BLAST and GFF coordinates are 1-based and inclusive.

- Subject bounds are
  `[min(sstart, send), max(sstart, send)]`.
- Subject strand is `+1` when `sstart <= send`, otherwise `-1`.
- Query bounds are normalized separately and must never be compared to genomic
  subject bounds.
- Left/right expansion is calculated in ascending genomic coordinates,
  independently of gene strand.
- Two intervals overlap only when they share at least one genomic position;
  adjacent intervals do not overlap.

Sort qualifying hits by:

1. quality descending;
2. genomic start ascending;
3. genomic end ascending;
4. query/model ID ascending;
5. chromosome ID ascending; and
6. strand ascending.

The first two keys implement the approved `(score, hsp.start)` policy while
the remaining keys make exact ties deterministic. Duplicate identical rows
must not cause duplicate discovery or repeated expansion.

## 6. Candidate construction algorithm

### 6.1 One preparation pass

Parse and filter the BLASTN file once per top-level invocation. Store
qualifying `BlastnHit`-like immutable records in a chromosome-keyed dictionary.
Both existing-locus expansion and new-locus discovery consume that prepared
evidence. Neither helper may reopen or reparse the raw BLASTN file.

The V0 helper boundaries remain preferred:

- `blastn_desired_expansion(...)`; and
- `blastn_new_loci_discovery(...)`.

Names may be adjusted for clarity, but the parsing, matching, and serialization
responsibilities must remain independently unit-testable in the new module.

### 6.2 Per-chromosome integration order

For each chromosome after protein candidates have passed
`keep_best_non_overlaping_loci()` and before final expansion:

1. index protein candidates by model ID;
2. process qualifying BLASTN hits in the deterministic order from Section
   5.4;
3. try same-model expansion first;
4. if no same-model candidate has positive overlap, try nucleotide-only
   discovery;
5. incorporate accepted nucleotide-only bounds as blockers for later hits;
6. reconcile the desired bounds of protein candidates with their neighbors;
   and
7. return all candidates sorted by genomic start.

### 6.3 Existing-locus expansion

For hit `[Hstart, Hend]`, consider only protein-derived candidates with the
same chromosome and model ID. Select the candidate with greatest positive
genomic overlap. Resolve an equal overlap by existing protein score descending,
then candidate start/end ascending.

For selected candidate `[Cstart, Cend]`, request:

```text
left  = max(0, Cstart - Hstart)
right = max(0, Hend - Cend)
```

Across multiple assigned hits, take the maximum request independently on each
side. BLASTN can never shrink a candidate. Combine BLASTN demand with existing
default, missing-protein, and template-GFF demand using the maximum on each
side. The existing neighbor-aware reconciliation remains responsible for
preventing final candidate overlap.

This logic must run even when `ParametersCandidateLoci.expansion is None`.
In that case only BLASTN-derived demand exists; no generic flank is introduced.

### 6.4 Nucleotide-only discovery

A qualifying hit becomes a nucleotide-only candidate only when it has no
positive overlap with:

- any accepted protein-derived candidate, regardless of model ID; or
- any earlier accepted BLASTN-derived candidate.

Thus protein evidence is always primary, and a higher-ranked BLASTN hit wins
over a lower-ranked overlapping BLASTN hit. Discarded hits do not replace or
change the model association of an accepted candidate.

The new candidate uses the normalized subject hit bounds and strand exactly.
It requests zero generic/missing-protein expansion and must not run through
protein-coordinate missing-part logic. It participates as a fixed-bound
neighbor when protein-derived expansions are reconciled.

### 6.5 Source-aware `CandidateLocus`

Add a source/origin field with a backward-compatible default for existing
constructor call sites. It must distinguish protein-derived from
nucleotide-only candidates.

When BLASTN mode is active, GFF column 2 is:

- `candidateLoci_blastp` for a protein-derived candidate, including one whose
  bounds were expanded by BLASTN; and
- `candidateLoci_blastn` for a nucleotide-only candidate.

Without a BLASTN file, preserve the legacy `candidateLoci` source label and
the existing GFF output structure. This compatibility rule avoids changing
the default pipeline while providing the requested source distinction in
BLASTN-enabled output.

Protein-derived candidates continue to serialize their existing `gene`,
`mRNA`, and HSP-derived `CDS` features unchanged apart from the BLASTN-mode
source label. Nucleotide-only candidates serialize exactly one `gene` and one
child `mRNA`, both spanning the BLASTN subject hit. They serialize no `CDS`
features and never present a BLASTN HSP as an exon.

For a nucleotide-only candidate, populate the existing metric fields as:

```text
prot_len / protLg = reference protein_length from the model GFF
nident            = BLASTN nident
pc_similarity     = coverage * identity
score             = protein_length * coverage * identity
```

`protLg` therefore retains its existing amino-acid meaning for both BLASTP-
and BLASTN-derived candidates. The BLASTN-only score is comparable in essence
to the protein-derived score, making the existing CLI score threshold
meaningful. It still does not compete with a protein score during overlap
selection because protein-derived candidates have priority. After non-overlap
discovery, apply the existing
`ParametersLociScoring.min_score` and `min_similarity` thresholds to the
BLASTN-derived score and `pc_similarity` before final acceptance.

If a nucleotide-only candidate fails those final filters, discard it and do
not let it block a later qualifying hit.

## 7. Optional behavior and edge cases

1. No `blastn_file`: exact legacy algorithm; no BLASTN parser/configuration is
   initialized.
2. Empty BLASTN file or no qualifying HSP: legacy protein-only candidate set.
3. `expansion=None` with BLASTN: discovery and evidence-based expansion still
   run; generic expansion does not.
4. `--ignore_gff_for_expansion`: disables template-derived expansion only; it
   does not disable BLASTN or permit an unknown query ID.
5. `--chr`: excludes all protein and BLASTN evidence for other chromosomes and
   creates no excluded chromosome keys.
6. Reverse subject HSP: normalized once; emitted candidate retains `-` strand.
7. Multiple hits for one candidate: union of requested outer bounds,
   independent of row order.
8. One hit overlapping two same-model candidates: greatest overlap, then the
   deterministic tie rule.
9. Different-model overlap: discard the BLASTN hit.
10. Nested, one-base-overlap, adjacency, and duplicate-hit cases follow the
    interval contract in Section 5.4.
11. A subject chromosome absent from protein results may receive a new
    BLASTN-only chromosome key.
12. At genomic start, final GFF coordinates remain positive and 1-based.
13. Chromosome-end clamping remains out of scope because chromosome lengths
    are not available in this flow.
14. If neighbor reconciliation clips a requested protein expansion, retain
    non-overlap and report the clipping in diagnostics.

## 8. Errors, diagnostics, and panic-risk requirements

### 8.1 Fail-fast input errors

The following abort the operation with an informative exception:

- missing/unreadable BLASTN file;
- invalid thresholds;
- inconsistent or insufficient column counts;
- malformed required fields or invalid coordinates;
- unknown query/model ID in a qualifying row; and
- internal interval/source invariants that would create an invalid candidate.

Never continue with a partially parsed BLASTN file after these errors.

### 8.2 Data-flow safety

- Keep raw protein input, sorted protein HSP input, and raw BLASTN input in
  distinct parameters and validation paths.
- Parse BLASTN exactly once and pass the same prepared evidence to both
  integration operations.
- Never treat BLASTN `qlen` as an amino-acid length. Use it only for nucleotide
  coverage and query-coordinate validation; obtain `prot_len` from the GFF.
- Never compare query coordinates with genomic subject coordinates.
- Normalize reverse coordinates once only.
- Apply a chromosome filter identically to both evidence sources.

### 8.3 CLI/output safety

- Validate all inputs before replacing outputs.
- Stage the GFF and query/target list so both correspond to one completed
  candidate set; a failure must not leave a new GFF paired with a stale list.
- Temporary files must be unique and removed on success or failure without
  deleting prior successful outputs.
- New source values and attributes must remain valid GFF and must not break
  downstream extraction or query/target association parsing.
- A nucleotide-only candidate must emit a valid model ID and strand in
  `as_query_target()` despite having no CDS features.

### 8.4 Diagnostics

One concise summary per invocation must include:

- BLASTN path and fixed thresholds;
- raw nonblank row count and qualifying row count;
- expanded protein-locus count;
- accepted nucleotide-only count;
- discarded overlap/filter counts; and
- clipped-expansion count.

Normal runs must not log every HSP. Errors must identify file, line, and bad
field/ID without dumping the full table.

## 11. Benchmark expectations

Use a production-representative wheat BLASTN table when available; otherwise
use a deterministic synthetic multi-chromosome table with a realistic small
qualifying fraction. Record:

- bytes, total rows, and qualifying rows;
- qualifying rows per chromosome;
- parsing/filtering and integration wall time;
- peak resident memory;
- expanded/new/discarded counts; and
- comparison with the no-BLASTN path.

Acceptance expectations:

1. raw input is scanned once;
2. memory stores only minimal qualifying-hit records, not the full table or
   unused columns;
3. adding 10x non-qualifying rows increases scan time approximately linearly
   but does not cause approximately 10x retained-memory growth;
4. no-BLASTN overhead remains within measurement noise; and
5. the implementation report includes commands and observed values rather
   than an invented hardware-independent time limit.

If real data shows that qualifying hits are numerous enough to threaten
memory, report the evidence and propose chromosome streaming as a follow-up;
do not add external sorting speculatively in this version.

## 12. Risks and mitigations

| Risk | Required mitigation |
|---|---|
| Flexible trailing columns hide a wrong producer | Fix semantics of the first ten columns, require uniform row width, and document the exact production command. |
| Strict thresholds still retain many wheat hits | Store minimal records, benchmark peak memory, and report qualifying counts. |
| Low-quality hit blocks a better hit | Process quality descending and only let accepted higher-ranked hits block later hits. |
| Paralogous hit changes a protein association | Protein candidates are primary; discard different-model overlap. |
| Reverse hit expands the wrong side | Normalize subject coordinates once and test strand-symmetric cases. |
| Wrong transcript or genomic span is used for `protLg` | Require one mRNA, sum its inclusive CDS lengths, divide by three, store the result in shared GFF metadata, and test multi-CDS models. |
| BLASTN HSP is emitted as CDS | BLASTN-only serializer emits gene + mRNA only. |
| BLASTN changes default behavior | No file means legacy path and source label; full suite must pass. |
| Two CLI outputs diverge on failure | Stage both outputs and replace only after successful candidate construction. |
| Neighbor clipping prevents requested coverage | Preserve non-overlap, count/report clipping, and test it explicitly. |

## 15. Model introspection

### Assumptions now made explicit

- BLASTN query IDs and protein model IDs use the same namespace.
- BLASTN subject coordinates are whole-genome coordinates in the same space as
  the candidate GFF.
- `qlen` is nucleotide locus length and is used only for BLASTN coverage and
  query-coordinate validation; reference-GFF CDS features define protein
  length.
- Every model used by this workflow has exactly one mRNA whose total CDS length
  is positive and divisible by three.
- Strict eligibility keeps the in-memory accepted-hit subset small enough for
  the first implementation.
- Protein evidence remains authoritative whenever intervals overlap.
- The exact self hits in the fixture drive the two required outcomes.

### Judgment calls retained in V2

- The approved `(score, hsp.start)` order is interpreted as quality descending
  and start ascending because higher-score hits must block lower-score hits.
- Additional deterministic tie fields are specified because score and start
  alone can still tie.
- Protein-derived output uses `candidateLoci_blastp` only in BLASTN-enabled
  mode; the no-BLASTN path retains `candidateLoci` to satisfy the original
  compatibility requirement.
- BLASTN-only loci receive zero generic expansion because the user requested
  gene/mRNA bounds from the hit; having a true protein length still does not
  provide a protein-to-genome HSP path for missing-part expansion.
- A non-divisible CDS length is treated as invalid reference metadata rather
  than rounded or truncated, so a computed protein length cannot silently be
  off by one amino acid.
- Malformed rows fail fast, while non-qualifying valid rows are simply counted
  and discarded.

These judgments are implementation requirements for V2. Reversing one requires
an explicit specification change rather than an implementation-only change.

## 16. Open questions

None. V2 is ready for implementation after approval.
