# BLASTN-guided candidate-locus discovery and expansion — specification V1

## 1. Status and scope

This document refines `TASKS/CandidateLoci_blastn/V0.md`. It is a planning
specification only: this task must not implement the feature or edit the
tentative tests.

The implementation goal is to optionally use high-confidence nucleotide BLAST
hits to:

1. expand a protein-derived candidate locus when BLASTP/TBLASTN evidence
   truncates the genomic region; and
2. add a candidate locus that protein evidence failed to discover.

All existing behavior must remain unchanged when no BLASTN input is supplied.
The bulk of the new logic should live in a separate, focused module. Changes to
`SCRIPT/CANDIDATE_LOCI/candidate_loci.py`,
`SCRIPT/CANDIDATE_LOCI/blast_utils.py`, and
`SCRIPT/candidate_loci_VR.py` should be limited to the integration points and
configuration needed by the approved design.

This V1 deliberately leaves significant choices open. Implementation must not
start until the choices marked **USER DECISION NEEDED** are resolved in this
spec or a later version.

## 2. Preserved background and motivating failures

The newly planned nucleotide locus-alignment transfer strategy is useful only
when model and target loci have high nucleotide similarity. Its success still
depends on the candidate-locus extraction step providing the complete target
region.

Candidate loci are currently inferred solely from protein-alignment HSPs.
Protein evidence can omit an exon or an entire locus even when the nucleotide
sequence is essentially identical. A truncated extracted region prevents the
nucleotide transfer strategy from recovering the full annotation.

The supplied regression fixture is:

`SCRIPT/CANDIDATE_LOCI/tests/data/OsjNip_HIPP_Nip2Nip_Chr04_19814005`

It intentionally compares Nipponbare genes to the same genome, so qualifying
self BLASTN hits have 100% query coverage and 100% identity. The fixture
contains:

- `ref.gff`: seven expected genes on `Chr4`;
- `blastn.tsv`: nucleotide hits, including one exact full-length self hit for
  each expected gene;
- `blastp_softmax.tsv`: protein evidence that finds all seven candidate
  regions, but truncates `OsjNip_Chr04_19814005`;
- `blastp_default.tsv`: protein evidence for which the
  `OsjNip_Chr04_19836437` locus is completely missed; and
- `readme.txt`: the original coverage evidence.

The observed failures that must remain part of acceptance are:

- Softmax BLASTP: `OsjNip_Chr04_19814005` is represented only over part of
  `Chr4:19812328-19814005`, covering 918 of 1,678 genomic bases (54.71%).
- Default BLASTP: `OsjNip_Chr04_19836437` at
  `Chr4:19835501-19836437` has zero covered bases and is absent as a complete
  candidate locus.

The tentative tests at the end of
`SCRIPT/CANDIDATE_LOCI/tests/test_candidate_loci.py` express the intended
seven-locus result, but are not executable specifications yet. They use
`Bounds[...]` instead of `Bounds(...)`, pass a third positional argument that
the current `find_candidate_loci` API does not accept, and use the misleading
name `blastp_sofmax_tsv` in the default-BLASTP case. The implementation phase
must adjust them after the public API decision in Section 11.

## 3. Existing architecture and feasible integration points

The current flow is:

1. `find_candidate_loci()` converts the raw 13-column protein BLAST table to
   sorted in-memory HSP rows.
2. `find_candidate_loci_from_file()` clusters protein HSPs by chromosome,
   strand, and model ID.
3. `keep_best_non_overlaping_loci()` removes overlapping protein-derived
   candidates using their protein-based score.
4. `expands()` calls `set_desired_expansion()`, then reconciles desired left
   and right expansion with chromosome order and neighboring candidate loci.
5. `CandidateLocus.as_gff()` and `.as_query_target()` feed the existing
   extraction/annotation pipeline.

The two integration points proposed in V0 are feasible:

- nucleotide-only discovery can occur after
  `keep_best_non_overlaping_loci()` has selected protein-derived loci for a
  chromosome and before final expansion; and
- a BLASTN-derived desired boundary can be incorporated after the default
  `ExpansionPair` is initialized in `set_desired_expansion()`, before
  `expands()` reconciles neighbors.

However, direct calls with a BLASTN file from both locations would parse the
same potentially huge file repeatedly. The implementation must parse/filter
once and pass a prepared per-chromosome view to both operations.

Creating a nucleotide-only `CandidateLocus` is not currently a neutral
operation. The class requires protein-coordinate paths and protein-derived
score fields, and `as_gff()` formats `score` and `pc_similarity` as floats.
The representation and ranking of nucleotide-only loci therefore require an
explicit decision rather than arbitrary placeholder values.

## 4. Terminology and coordinate contract

- A **raw BLASTN HSP** is one input table row. HSPs are assessed individually;
  they are not merged to pass the eligibility thresholds.
- A **qualifying hit** is a raw HSP satisfying both configured thresholds.
- Query coverage is `alignment_length / query_length`.
- Identity is `pident / 100`.
- Default thresholds are inclusive: coverage `>= 0.85` and identity `>= 0.95`,
  matching `TASKS/NT_annotation_transfert/planning_NT_transfert_V3.md`.
- BLAST query ID is the model/protein association ID used by candidate loci.
  Whether unknown IDs are rejected or skipped remains Question 4.3.
- BLAST subject ID is the target chromosome/contig ID and must match the
  chromosome namespace used by protein-derived candidates.
- BLAST coordinates are 1-based and inclusive. Normalize subject bounds to
  `[min(sstart, send), max(sstart, send)]`; retain strand as `+1` when
  `sstart <= send` and `-1` otherwise.
- Genomic left/right expansion is calculated in ascending chromosome
  coordinates, independently of gene strand. Strand is still retained for
  candidate identity and downstream output.
- Two intervals overlap only if they share at least one 1-based genomic
  position. Merely adjacent intervals do not overlap.
- Coverage and identity must be computed from raw, unrounded values. Values
  shown in diagnostics may be rounded, but filtering must not be.

### Input-format discrepancy

The supplied BLASTN fixture has 14 tab-separated fields:

`qseqid sseqid qlen length qstart qend sstart send nident pident gapopen evalue bitscore positive`

The current protein parser expects 13 fields and omits `positive`. The
nucleotide transfer task documents a different 12-field BLASTN schema, with
`bitscore` before `evalue` and no `gapopen` or `positive`. A strict accepted
schema is a panic-risk boundary and is unresolved in Decision 2.

## 5. Functional requirements

### 5.1 Optional activation and compatibility

1. BLASTN-guided behavior must be opt-in.
2. With no BLASTN input, the public Python APIs, CLI defaults, selected loci,
   locus ordering, bounds, GFF output, query/target list, and error behavior
   must remain unchanged.
3. Existing callers must not be forced to construct new configuration
   objects.
4. When a chromosome filter is supplied, it must apply consistently to both
   protein and nucleotide inputs.
5. The CLI must verify a supplied BLASTN path exists before creating or
   replacing outputs.
6. Minimum coverage and identity must default to `0.85` and `0.95`. Invalid
   thresholds outside `[0, 1]` must fail before parsing alignments.

### 5.2 Parse and filter once

1. Read the BLASTN input once per top-level candidate-locus invocation.
2. Validate the approved exact column schema, field types, positive query
   length, positive alignment length, percentage identity in `[0, 100]`, and
   positive 1-based coordinates.
3. Calculate coverage and normalized identity, retaining only qualifying
   individual HSPs.
4. Retain at least query/model ID, chromosome, normalized genomic bounds,
   strand, query length, alignment length, coverage, identity, bit score, and
   e-value when present in the approved schema.
5. Provide qualifying hits in deterministic chromosome and genomic order to
   discovery and expansion logic.
6. Avoid memory proportional to the complete unfiltered wheat BLASTN file.
   The precise bounded-memory strategy remains Decision 3.
7. Do not silently reinterpret a protein BLAST table as the BLASTN table or
   vice versa.

The V0 suggestion of a readable immutable record (`namedtuple`, `attrs`
class, or dataclass) and a chromosome-keyed prepared view is preserved as a
design preference. The final container must satisfy the bounded-memory
requirement rather than necessarily being one in-memory hash table.

### 5.3 Expand an existing protein-derived locus

For each chromosome:

1. Build a model ID to candidate-loci index for the protein-derived candidates
   surviving overlap filtering.
2. Consider qualifying BLASTN hits whose query/model ID occurs in that index.
3. Match each hit only to a candidate with the same chromosome and model ID.
4. Select the candidate having the greatest positive genomic overlap with the
   hit. Hits with zero overlap do not expand an existing candidate and proceed
   to nucleotide-only discovery.
5. For a matched candidate with current bounds `[Cstart, Cend]` and hit bounds
   `[Hstart, Hend]`, request at least:
   - left expansion `max(0, Cstart - Hstart)`; and
   - right expansion `max(0, Hend - Cend)`.
6. Combine BLASTN-derived demand with the existing default, missing-protein,
   and template-GFF demand by taking the maximum independently on each genomic
   side. BLASTN must never shrink a candidate.
7. Preserve the existing final neighbor-aware expansion stage. BLASTN
   establishes desired bounds; it does not bypass collision handling or force
   overlapping final candidate loci.
8. The result must be independent of input row order. Tie-breaking and the
   treatment of multiple qualifying hits are resolved in Decision 4.

For the softmax fixture, the qualifying exact hit for
`OsjNip_Chr04_19814005` must extend its candidate to cover the entire
`19812328-19814005` interval when default expansion values are zero and no
neighbor conflict prevents it.

### 5.4 Discover nucleotide-only loci

For each qualifying hit not assigned to an overlapping protein-derived
candidate:

1. Compare it to all already accepted candidate intervals on the same
   chromosome, including nucleotide-only loci accepted earlier in the
   deterministic ranking.
2. If it overlaps an accepted locus, apply the approved conflict policy rather
   than emitting two overlapping final candidates.
3. If it does not overlap, create one candidate association using the hit
   bounds, query/model ID, subject chromosome, and hit strand.
4. Mark the candidate's origin so downstream code can distinguish
   `protein`, `blastn`, or combined evidence. The precise representation and
   score contract remain Decision 5.
5. Do not apply protein-missing-part expansion logic to fields that are
   unknown or synthetic for a nucleotide-only locus.
6. Include new loci in chromosome-coordinate sorting and neighbor-aware
   expansion so final loci remain non-overlapping.

For the default-BLASTP fixture, the exact qualifying hit for
`OsjNip_Chr04_19836437` must add a candidate covering
`Chr4:19835501-19836437`.

### 5.5 Determinism and diagnostics

1. Candidate results must be deterministic for any permutation of equivalent
   BLASTN rows.
2. Qualifying-hit ordering and all tie-breakers must be explicitly encoded and
   unit tested.
3. At minimum, logging/diagnostics must report the BLASTN file, thresholds,
   raw row count, qualifying row count, counts of expanded and newly
   discovered loci, and counts/reasons for skipped hits.
4. Normal successful runs must not print one line per hit.
5. Malformed input and invariant violations must identify the file and line
   number without dumping sequence data or the whole table.

## 6. Significant design decisions

### Decision 1 — Python API and CLI configuration

Why this matters: the tentative tests assume a third positional BLASTN
argument, but adding it before `params` would break positional callers. The
feature also needs thresholds and must remain off by default.

**A. Add a keyword-only `blastn_file` plus a dedicated optional BLASTN
configuration object**

- Pros: preserves existing positional calls; groups file, thresholds, and
  future parser policy; easy to keep disabled with `None`.
- Cons: requires threading a new object through two public functions and the
  CLI.

**B. Add separate keyword arguments (`blastn_file`, minimum coverage, minimum
identity)**

- Pros: simple at the call site; no additional configuration type.
- Cons: expands signatures and makes future BLASTN settings harder to manage.

**C. Put BLASTN settings inside `ParametersCandidateLoci`**

- Pros: one existing configuration entry point.
- Cons: couples an input file to algorithm parameters and makes direct
  `find_candidate_loci_from_file()` use less clear.

Recommendation: **A**, with an optional CLI flag such as `--blastn-table` and
explicit threshold flags. Update tentative tests to use the approved keyword
form.

**USER DECISION NEEDED — answer Questions 1.1 and 1.2.**

### Decision 2 — accepted BLASTN table schema

Why this matters: accepting the wrong column order can swap e-value and bit
score or silently use the wrong field for filtering/ranking.

**A. Require exactly the supplied 14-column schema**

- Pros: directly supports the regression fixture; strict and easy to validate.
- Cons: differs from the nucleotide-transfer task's 12-column schema.

**B. Require one new canonical 12-column schema and update the fixture**

- Pros: shares a schema with nucleotide transfer; fewer unused fields.
- Cons: mutates supplied test data and may not match the production BLAST
  command that created it.

**C. Support both exact schemas through an explicit format selector**

- Pros: interoperates with both existing artifacts without guessing.
- Cons: more parser and test surface.

Recommendation: **C** only if both producers will remain in use; otherwise
standardize on **A** for this task and document the exact generating
`-outfmt`. Never infer schema solely from field count when two supported
formats could be ambiguous.

**USER DECISION NEEDED — answer Questions 2.1 and 2.2.**

### Decision 3 — bounded-memory preparation

Why this matters: V0 explicitly warns that wheat BLASTN output may be huge. A
dictionary containing every qualifying hit can still exhaust memory even
though the raw file is streamed.

**A. Require chromosome-grouped input and stream one chromosome at a time**

- Pros: simplest and fastest bounded-memory algorithm.
- Cons: imposes a precondition; must detect a chromosome reappearing later.

**B. Filter once into a temporary file, externally sort by chromosome and
coordinates, then stream chromosome batches**

- Pros: bounded memory for unsorted input; preserves a simple per-chromosome
  consumer.
- Cons: extra disk I/O, temporary-file cleanup, and sorter dependency/code.

**C. Store all qualifying hits in a chromosome-keyed in-memory dictionary**

- Pros: closest to V0 pseudocode; simplest random access.
- Cons: does not meet the stated wheat-scale memory requirement in the worst
  case.

Recommendation: **B** unless the production BLASTN generation step can
guarantee chromosome-grouped output, in which case **A** is preferable.

**USER DECISION NEEDED — answer Question 3.1.**

### Decision 4 — hit assignment, ranking, and conflicts

Why this matters: paralogous hits can overlap multiple protein candidates or
each other. `coverage * identity` alone often ties exact hits and omits
alignment length and statistical support.

**A. Greedy global hit ranking**

- Rank by coverage descending, identity descending, aligned length descending,
  bit score descending, e-value ascending, then IDs and coordinates ascending.
  Assign each hit to its greatest-overlap same-model candidate; otherwise add
  it only if it does not overlap an accepted locus.
- Pros: deterministic and close to V0's score-first proposal.
- Cons: an early hit can block a later hit for another model.

**B. Best hit per `(model ID, chromosome, locus cluster)` before assignment**

- Pros: reduces duplicate HSPs and repeated evidence.
- Cons: requires a defined clustering distance/overlap rule and can discard
  legitimate duplicated loci.

**C. Combine all compatible hits per candidate/new-locus component**

- Pros: can use fragmented nucleotide evidence.
- Cons: conflicts with the requirement that one individual HSP pass coverage,
  and adds substantial clustering complexity.

Recommendation: **A** for the first implementation, using all qualifying hits
assigned to an existing candidate to grow the union of desired bounds. Resolve
equal-overlap candidate ties with the candidate's existing score and then
coordinates. Do not merge separate hits to make an ineligible HSP eligible.

**USER DECISION NEEDED — answer Questions 4.1 through 4.3.**

### Decision 5 — nucleotide-only `CandidateLocus` representation and score

Why this matters: a BLASTN query length is nucleotide length, not the
`CandidateLocus.prot_len` amino-acid length. Fabricating protein paths or
scores can corrupt downstream output and later protein-based expansion.

**A. Extend `CandidateLocus` with evidence origin and explicitly optional
protein-only fields**

- Pros: honest data model; downstream guards are visible and testable.
- Cons: touches more existing code and output formatting.

**B. Introduce a separate candidate seed/evidence type, then construct a
fully valid `CandidateLocus` using model information from the GFF**

- Pros: isolates BLASTN parsing and keeps final output type uniform.
- Cons: model GFF may not provide every required protein metric; conversion
  rules and missing-ID behavior must be explicit.

**C. Fill existing fields with neutral/synthetic values and add only a source
flag**

- Pros: smallest code change.
- Cons: misleading scores/paths; high risk of accidental use and formatted
  `None` failures.

Recommendation: **B** if the GFF can authoritatively supply every model ID
used in production; otherwise **A**. Reject **C**.

**USER DECISION NEEDED — answer Questions 5.1 and 5.2.**

### Decision 6 — interaction with `expansion=None`

Why this matters: `expansion=None` currently means no generic candidate
expansion. Supplying BLASTN is separately an explicit opt-in, so either
interpretation is plausible.

**A. BLASTN discovery and BLASTN boundary expansion still run**

- Pros: an explicit BLASTN input does what its name promises; generic flanks
  remain disabled.
- Cons: changes bounds even though `expansion=None`.

**B. Discovery runs, but existing candidates are not expanded**

- Pros: separates locus discovery from expansion.
- Cons: fails the softmax motivating case under `expansion=None`.

**C. All BLASTN behavior is disabled when `expansion=None`**

- Pros: preserves the broadest meaning of “no expansion.”
- Cons: silently ignores an explicitly supplied BLASTN input and also disables
  discovery.

Recommendation: **A**, documenting that `expansion=None` disables heuristic
flanks, not an explicitly requested evidence source.

**USER DECISION NEEDED — answer Question 1.3.**

## 7. Edge cases and required behavior

1. Empty BLASTN file: succeed with the exact legacy protein-only result and
   zero BLASTN actions.
2. No qualifying rows: same as an empty BLASTN file.
3. Threshold equality: rows exactly at 0.85 coverage or 0.95 identity qualify.
4. Reverse hit: normalize bounds once, retain `-1`, and never subtract from the
   wrong genomic side.
5. Query longer/shorter than aligned row: use declared `qlen`; reject zero or
   negative values.
6. Query ID absent from the template GFF/protein metadata: follow the approved
   missing-ID policy; never construct a partially invalid candidate by
   accident.
7. Subject chromosome absent from protein-derived results: nucleotide-only
   discovery may create the chromosome key if allowed by the approved
   representation.
8. Chromosome filter excludes all nucleotide hits: do not create excluded
   chromosome keys.
9. Duplicate identical rows: they must not produce duplicate loci or repeated
   expansion.
10. Multiple hits for one existing candidate: final desired bounds must be
    order-independent.
11. One hit overlaps two candidates for the same model: use the approved
    greatest-overlap and tie policy.
12. One hit overlaps a candidate for a different model: apply the approved
    conflict policy; never emit overlapping final loci silently.
13. Nested, touching, and one-base-overlap intervals: test all three under the
    coordinate contract.
14. Neighbor constraint prevents full requested expansion: preserve
    non-overlap and expose that the BLASTN desired bound was clipped.
15. Candidate at chromosome start: clamp the final start consistently with
    existing behavior and never emit a negative/zero coordinate under the
    approved 1-based contract.
16. Candidate at chromosome end: the current code cannot clamp without
    chromosome lengths. Preserve current behavior unless lengths are added by
    a separately approved scope change.
17. Missing, unreadable, malformed, truncated, or mixed-schema BLASTN input:
    fail before replacing successful prior outputs.
18. NaN/infinite numeric fields: reject as malformed.
19. A chromosome occurring in multiple non-contiguous batches under streaming
    option A: fail with a clear sorting-precondition error.
20. Generic expansion disabled: follow Decision 6 and test it explicitly.

## 8. Panic-risk requirements

These are correctness boundaries where silent recovery could produce the
wrong genomic interval or query/target association.

### 8.1 Data-flow risks

- The raw protein table, sorted protein HSP stream, and BLASTN table must have
  distinct parameter names and types/validation paths.
- BLASTN must be parsed once per invocation; discovery and expansion must
  consume the same filtered evidence.
- Temporary sorted/filtered files must be uniquely created, closed before
  reading, and removed on success or failure. Existing output files must not
  be deleted as part of temporary cleanup.
- An exception during BLASTN preparation must prevent partial candidate GFF or
  query/target list replacement.
- If the CLI writes two outputs, they must represent the same completed
  candidate set. A failure between writes must not leave a new GFF paired with
  a stale association list; use atomic replacement or equivalent staging.

### 8.2 Coordinate-space risks

- Never compare BLAST query coordinates to target genomic coordinates.
- Never treat BLASTN `qlen` as amino-acid `prot_len`.
- Normalize reverse subject coordinates exactly once.
- Keep BLAST 1-based inclusive bounds consistent with `Bounds` and GFF.
- Calculate desired left/right extension in ascending genomic coordinates,
  then retain strand separately.
- Apply any chromosome offset conversion exactly once; this feature consumes
  genome-coordinate BLAST subject positions in the supplied fixture.
- Detect and fail on invalid intervals instead of swapping arbitrary malformed
  values other than the valid reverse-strand `sstart > send` case.

### 8.3 CLI and flag-combination risks

- No BLASTN path means BLASTN thresholds have no effect and legacy behavior is
  exact.
- Supplying BLASTN-specific threshold/format flags without a BLASTN path must
  either fail as a usage error or emit an explicit warning, as decided in
  Question 1.2; it must not silently suggest the feature ran.
- `--chr` must filter both evidence sources identically.
- `--ignore_gff_for_expansion` must not cause invalid nucleotide-only model
  metadata or silently change the chosen representation.
- The approved `expansion=None` semantics must be consistent between direct
  Python calls and CLI construction.

### 8.4 Script-integration risks

- Preserve the current `candidate_loci_VR.py` output formats consumed by locus
  extraction and `genePrediction.sh`.
- A nucleotide-only candidate must still yield a valid query/model ID and a
  valid target strand in the association list.
- GFF diagnostic attributes for source or BLASTN quality must not break
  downstream attribute parsing.
- Do not use BLASTN hit blocks as biological CDS annotations; `chr_path` in
  candidate output is evidence, not a transferred exon structure.

## 9. Risks and mitigations

| Risk | Impact | Required mitigation |
|---|---|---|
| Large qualifying-hit set on wheat | Memory exhaustion | Approve and benchmark Decision 3; avoid whole-file materialization. |
| Paralogous high-identity hits | Wrong model/locus association | Same-model matching, deterministic ranking, conflict tests, source diagnostics. |
| Misread BLAST schema | Wrong thresholds or ranking | Exact schema contract/selector and strict row validation. |
| Reverse-coordinate error | Expansion on wrong side | Normalize once and test forward/reverse equivalents. |
| Synthetic protein fields | Corrupt score/output or crash | Resolve Decision 5; forbid undocumented placeholders. |
| New locus overlaps existing locus after expansion | Ambiguous extracted regions | Use existing neighbor-aware reconciliation and assert final non-overlap. |
| Optional feature changes legacy output | Pipeline regression | Byte-level/no-BLASTN regression where output order is stable, plus full candidate-locus tests. |
| Temporary-file or two-output failure | Stale/mismatched artifacts | Staged output and cleanup failure-path tests. |
| Per-hit interval scan | Poor runtime with many loci/hits | Use sorted sweeps or an interval index; benchmark asymptotic behavior. |

## 10. Implementation phases

Implementation is explicitly out of scope for this refinement task. After the
open decisions are approved, implementation should proceed in these phases.

### Phase 1 — lock contracts and make tentative tests valid

1. Record answers in this spec or V2.
2. Correct `Bounds[...]` to `Bounds(...)`.
3. Update the two tentative tests to the approved keyword/API contract and
   clear variable names.
4. First demonstrate the two motivating tests fail for the expected missing
   functionality, not due to syntax or argument errors.

### Phase 2 — isolated BLASTN evidence module

1. Add the approved configuration and immutable hit/evidence types in a
   separate module.
2. Implement strict parsing, eligibility, normalization, deterministic
   ordering, diagnostics, and bounded-memory preparation.
3. Cover pure logic with small synthetic unit tests before integration.

### Phase 3 — existing-locus expansion

1. Build the per-model candidate index.
2. Assign overlapping same-model hits.
3. Merge desired genomic bounds with existing `ExpansionPair` demand.
4. Preserve neighbor-aware reconciliation and add clipped-demand diagnostics.
5. Make the softmax fixture pass.

### Phase 4 — nucleotide-only discovery

1. Implement the approved representation and score/source policy.
2. Add deterministic non-overlap conflict handling.
3. Integrate new candidates before final chromosome expansion/sorting.
4. Make the default-BLASTP fixture pass.

### Phase 5 — public API and CLI

1. Thread optional configuration through both Python entry points without
   breaking positional callers.
2. Add approved CLI flags, validation, chromosome filtering, and staged
   outputs.
3. Document the exact BLASTN generation command/schema.

### Phase 6 — regression and scale validation

Run the validation plan below, capture benchmark evidence, and write the task
report. Refactor only if results show duplicated parsing or difficult
integration; preserve KISS/YAGNI.

## 11. Validation plan

### 11.1 Validation tier

Use **Tier 2: focused unit tests + module regression + CLI fixture integration
+ bounded-memory benchmark**. No external BLAST execution is needed for the
core acceptance tests because the feature consumes supplied tabular results.

The implementation report must distinguish:

- baseline failures already present before implementation;
- tests made executable from the tentative drafts; and
- new failures introduced by the feature.

### 11.2 Required unit tests

1. Both thresholds, including exact boundary values and just-below values.
2. The approved 14/12-column schema behavior and malformed/mixed rows.
3. Forward and reverse coordinate normalization.
4. Empty input and no qualifying hits.
5. Duplicate rows and input-order permutation.
6. Greatest-overlap assignment, zero overlap, and equal-overlap tie.
7. Multiple hits expanding one candidate on the left, right, and both sides.
8. Different-model overlap conflict.
9. New chromosome discovery and chromosome filtering.
10. Origin/representation serialization without fabricated or `None`
    formatting failures.
11. `expansion=None` and `--ignore_gff_for_expansion` behavior.
12. One-base overlap, adjacency, nested intervals, and neighbor clipping.
13. Temporary preparation cleanup and malformed-input failure paths.

### 11.3 Required fixture tests

With `nb_nt_default=0` and `nb_nt_when_missing_part=0`, and using approved
BLASTN defaults:

1. Softmax protein input plus BLASTN yields seven `Chr4` candidates sorted by
   genomic start.
2. Default protein input plus BLASTN yields the same seven candidates.
3. Each candidate covers the corresponding reference gene interval:

   - `19796632-19797845`
   - `19812328-19814005`
   - `19819617-19820436`
   - `19822056-19822949`
   - `19826726-19827860`
   - `19835501-19836437`
   - `19841797-19842670`

4. If exact equality is approved in Question 6.1, assert exact bounds;
   otherwise assert containment plus final non-overlap.
5. The new default-BLASTP locus is associated with
   `OsjNip_Chr04_19836437` and marked as BLASTN-derived.
6. The expanded softmax locus is associated with
   `OsjNip_Chr04_19814005` and records combined evidence.

### 11.4 Compatibility regression

1. Run all tests in `SCRIPT/CANDIDATE_LOCI/tests`.
2. Run representative direct calls to both `find_candidate_loci()` and
   `find_candidate_loci_from_file()` without BLASTN.
3. Run `candidate_loci_VR.py` without BLASTN and compare candidate bounds,
   ordering, GFF, and association list against the pre-change result.
4. Run the CLI with the fixture and BLASTN enabled; verify both output files
   describe the same seven candidates.

### 11.5 Benchmark expectations

Benchmark on a production-representative wheat BLASTN table if one can be
shared; otherwise generate a deterministic synthetic table with multiple
chromosomes and a controlled qualifying fraction. Record:

- input bytes and rows;
- qualifying rows and chromosome distribution;
- wall time for preparation and candidate integration separately;
- peak resident memory;
- temporary disk usage; and
- expanded/new/skipped hit counts.

Acceptance expectations:

1. Runtime should scale approximately linearly with input rows plus sorting
   cost for the approved preparation strategy.
2. Peak memory must be bounded by the active chromosome/batch and candidate
   index, not the full unfiltered file size.
3. A 10x input created by adding non-qualifying rows must not produce roughly
   10x retained-memory growth.
4. No-BLASTN runtime and memory should remain within measurement noise of the
   legacy path because the feature is not initialized.
5. The report must give observed values and commands. Do not invent a fixed
   wall-time threshold before measuring the available hardware and dataset.

## 12. Code-quality constraints

The V0 principles remain requirements:

- Readability first: clear names, small focused functions, self-documenting
  types, and comments only where the biological/coordinate rule needs them.
- KISS: implement the simplest approved deterministic policy.
- DRY: parse and filter once; share interval and threshold logic rather than
  duplicating it between discovery and expansion.
- YAGNI: do not build generalized alignment clustering, database storage, or

## 15. Model introspection

### Assumptions made but not previously explicit

- The BLASTN query IDs and protein BLAST model IDs share the same identifier
  namespace because the fixture uses values such as
  `OsjNip_Chr04_19814005` in both.
- The BLASTN subject coordinates are already in the same whole-genome
  coordinate space as `CandidateLocus.chr_bounds` and `ref.gff`.
- The intended gate uses one individual HSP, coverage `length / qlen`, and
  `pident / 100`, based on the referenced nucleotide-transfer V3.
- Final candidate loci should remain non-overlapping because that is a current
  invariant of `keep_best_non_overlaping_loci()` and `expands()`.
- The exact self hits, not the lower-quality cross-gene hits in `blastn.tsv`,
  are intended to drive both fixture outcomes.

### Judgment calls that could be wrong

- Recommending a separate configuration object may be more abstraction than
  the project wants for three settings.
- Recommending external sorting assumes unsorted production input; upstream
  BLAST splitting or ordered concatenation may make streaming option A enough.
- Requiring same-model overlap for expansion may be too strict if model IDs
  are transformed between nucleotide and protein resources.
- Treating BLASTN input as explicit evidence even when `expansion=None` may
  conflict with existing caller expectations.
- Preserving neighbor-based clipping may prevent exact BLASTN coverage in
  dense tandem arrays; a future policy might prioritize a high-confidence
  nucleotide hit over an existing protein candidate.
- A separate nucleotide evidence type may be unnecessary if authoritative GFF
  metadata can always construct a semantically complete `CandidateLocus`.
