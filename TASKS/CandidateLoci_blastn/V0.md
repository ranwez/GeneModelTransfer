### blastn preparation and pre-filtering
Since the blastn file could be huge on wheat genome, we should not load it fully in memory. Moreover candidate loci are handle by chromosome. So we can prepare the blastn file by filtering it, keeping only the useful information of the relevant hits ordered organized by chromosome in a hashtable.
For each blastn hit, if the blastn hit has sufficent identity and coverage (same logic as nucleotide annotation transfert TASKS/NT_annotation_transfert/planning_NT_transfert_V3.md using default `0.85`, `0.95`), we extract the following information in basic structures (e.g. namedtuple or dataclass for readability):
- bounds of the hit (start, end); using existing bound structure
- coverage and identity of the hit; 
- protein id of the hit; 
The chromosome is not required since it will be implied by the key of the hashtable.
So the pseudo code for this function could be:
```python
filtered_blastn_hits = defaultdict(list)
for each line in blastn_results_file:
    parse the line to get chromosome, start, end, coverage, identity, protein_id 
    if coverage >= 0.85 and identity >= 0.95:
        filtered_blastn_hits[chromosome].append (new_hit(Bound(start, end), cov=coverage, id=identity))
for each chromosome in filtered_blastn_hits:
    sort the list of hits by start position
```

### blastn desired expansion of candidate loci (fixing blastp softmax issue in unit test)
We first parse candidate_loci and create a dictionnary having model protein as key and list of the candidate loci associated to this protein as value prot2Candidate.
 Then for each filtered_blastn_hits[current_chromosome], we will check if:
- the hit should be done by one of the model protein of prot2Candidate keys; if so save the corresponding candidate loci current_prot_candidates.
- identify the candidate of current_prot_candidates having maximum overlapping with the blastn hit (different chromosome mean 0 overlap)
- then get the nucleotide hit coordinates to adjust the candidate loci desired expansion. Note that this does not determine the final expansion, it just provides the desired expansion for this locus, this will be refine in next steps using gff informations and neighboring candidate loci to avoid overlapping candidate loci.

## Code Quality Principles

### 1. Readability First
- Code is read more than written
- Clear variable and function names
- Self-documenting code preferred over comments

### 2. KISS (Keep It Simple, Stupid)
- Simplest solution that works
- Avoid over-engineering
- No premature optimization
- Easy to understand > clever code

### 3. DRY (Don't Repeat Yourself)
- Extract common logic into functions
- Create reusable components
- Share utilities across modules
- Avoid copy-paste programming

### 4. YAGNI (You Aren't Gonna Need It)
- Don't build features before they're needed
- Avoid speculative generality
- Add complexity only when required
- Start simple, refactor when needed
